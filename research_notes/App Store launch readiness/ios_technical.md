# Technical production readiness: Capacitor 8 iOS app with HealthKit and local notifications

Researched 2026-11-10. Scope: what the Logbook binary and Xcode project must contain or do before App Store release. Policy topics (nutrition label answers, age rating, account deletion, AI disclosure, Strava terms) belong to other notes; they appear here only where they change a file in the iOS project.

Source type labels used on every item:
- **[Apple rule]** App Review Guidelines, App Store Connect validation, or Apple docs that say "must" / "required" / "rejects".
- **[Apple guidance]** Apple docs, HIG, technotes, WWDC sessions that advise without stating an enforcement.
- **[Vendor docs]** Official Capacitor, WebKit.org, Sentry documentation.
- **[Practitioner]** Forum threads, blogs. Lower confidence; flagged when I only saw a search summary and did not open the page.
- **[Repo]** Read directly from /home/user/LogBook at research time (file path given instead of URL).

How Apple pages were read: developer.apple.com documentation pages are JavaScript rendered, so I read their JSON source (`https://developer.apple.com/tutorials/data/documentation/<path>.json`) and quote from that. The URLs cited below are the human readable equivalents.

Dated changes that matter today (all traced to a source below):
- 2024-05-01: required reason API declarations enforced at upload.
- 2024-11-12: invalid privacy manifests rejected (ITMS-91056).
- 2025-02-12: listed third-party SDKs (Capacitor and Cordova are on the list) must carry a privacy manifest in new apps (ITMS-91061).
- 2026-04-28: uploads must be built with Xcode 26 or later and an OS 26 SDK.
- 2026-06-08 / 2026-09-14: TN3208, launch screen key required for builds made with the iOS 27 SDK (ITMS-90870).
- 2026-09-09: uploads must target iOS 13 or later.
- iOS 27 SDK: UIScene life cycle required or the app will not launch; `UIRequiresFullScreen` no longer opts out of resizing (corrected 2026-11-10: on iPhone as well as iPad, see IOS-36); HealthKit gains a "limited window of recent data" authorization state.

## 5. WKWebView specifics

### Takeaway
The risks specific to a web view shell are storage eviction, cookie behaviour, and anything that makes the app feel like a browser. Logbook has already handled most feel items natively (bounce, link previews, keyboard, safe areas, Dynamic Type). The remaining technical exposure is data kept only in web storage and unverified behaviour of streamed or large requests through CapacitorHttp.

### Cited Findings
- [Apple rule] Guideline 2.5.2: apps "should be self-contained in their bundles ... nor may they download, install, or execute code which introduces or changes features or functionality of the app". [2.5.2](https://developer.apple.com/app-store/review/guidelines/#2.5.2)
- [Apple rule] Guideline 4.7 applies to "software that is not embedded in the binary, specifically HTML5 and JavaScript mini apps and mini games, streaming games, chatbots, and plug-ins". [4.7](https://developer.apple.com/app-store/review/guidelines/#4.7)
- [Apple rule] Guideline 2.5.6: "Apps that browse the web must use the appropriate WebKit framework and WebKit JavaScript." [2.5.6](https://developer.apple.com/app-store/review/guidelines/#2.5.6)
- [Vendor docs] Storage: Local Storage "must be considered transient"; "your app needs to expect that the data will be lost eventually"; "the OS will reclaim local storage from Web Views if a device is running low on space"; "The same can be said for IndexedDB at least on iOS". Preferences "avoids the eviction issues" but "is meant for small amounts of data"; SQLite is suggested for larger data. [Capacitor storage guide](https://capacitorjs.com/docs/guides/storage)
- [Vendor docs] WebKit storage policy (Safari 17.0, "WebKit apps for iOS 17"): "For other apps, the origin quota is up to 15% of the total disk space" and "overall quota is up to 20%"; eviction happens "when exceeding the overall quota, when the system is under storage pressure" and for sites not used for some time under ITP; "the data of an origin will be deleted as a whole"; "Origin might be excluded from eviction if it has active page at the time of eviction, or its storage is in persistent mode"; persistence is granted "based on heuristics like whether the website is opened as a Home Screen Web App". Covered types: "localStorage, Cache API, IndexedDB, Service Worker, and File System"; "cookies and HTTP cache are currently not subject to the policy". [WebKit: Updates to Storage Policy](https://webkit.org/blog/14403/updates-to-storage-policy/)
- [Vendor docs] ITP: "Intelligent Tracking Prevention (ITP), is enabled by default in all WKWebView applications." [WebKit: App-Bound Domains](https://webkit.org/blog/10882/app-bound-domains/). The seven-day rule is written for Safari: "deleting all of a website's script-writable storage after seven days of Safari use without user interaction on the site". [WebKit: Full Third-Party Cookie Blocking](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)
- [Vendor docs] App-bound domains: up to 10 domains in `WKAppBoundDomains`; once set, script injection and message handlers work only on those domains with `limitsNavigationsToAppBoundDomains`. [WebKit: App-Bound Domains](https://webkit.org/blog/10882/app-bound-domains/). Capacitor: with the key present plugins can fail with "Plugin not implemented"; remove the key or set `limitsNavigationsToAppBoundDomains` true. [Capacitor troubleshooting](https://capacitorjs.com/docs/ios/troubleshooting)
- [Vendor docs] Cookies plugin: "provides native cookie support via patching document.cookie to use native libraries"; disabled by default; "As of iOS 14, you cannot use 3rd party cookies by default"; adding `WKAppBoundDomains` gives "better support for cookies on iOS". [Capacitor Cookies](https://capacitorjs.com/docs/apis/cookies)
- [Apple guidance] `HTTPCookieStorage`: "Each app and app extension has a unique data container, meaning they have separate cookie stores." "Session cookies (where the cookie object's isSessionOnly property is true) are local to a single process and are not shared." `isSessionOnly`: "whether the cookie should be discarded at the end of the session (regardless of expiration date)". [HTTPCookieStorage](https://developer.apple.com/documentation/foundation/httpcookiestorage) ; [isSessionOnly](https://developer.apple.com/documentation/foundation/httpcookie/issessiononly)
- [Vendor docs] HTTP plugin: enabling patches `window.fetch` and `XMLHttpRequest` "to use native libraries"; "On Android and iOS, data can only be a string or a JSON"; FormData, Blob and ArrayBuffer are supported only through the patched fetch/XHR; "parsing and transferring large amount of data from native to the web can cause issues", use `@capacitor/file-transfer`. The page says nothing about streamed responses. [Capacitor Http](https://capacitorjs.com/docs/apis/http)
- [Vendor docs] iOS config defaults: `contentInset` default `never`; `zoomEnabled` default false; `webContentsDebuggingEnabled` default false in release; `loggingBehavior` default `debug`; `handleApplicationNotifications` default true; `limitsNavigationsToAppBoundDomains` default false. "By default, external URLs open in the external browser." [Capacitor config](https://capacitorjs.com/docs/config)
- [Vendor docs] Safe areas: set `viewport-fit=cover`, then use `env(safe-area-inset-top|right|bottom|left)`; "constant() has been removed and replaced with env()"; combine with `max()` behind `@supports`. [WebKit: Designing Websites for iPhone X](https://webkit.org/blog/7929/designing-websites-for-iphone-x/)
- [Practitioner] (opened 2026-11-10 through the fetch tool) WebKit bug 206741, "WKWebView support for Service Workers", status NEW with no resolution. The statement that service workers do not load from a custom URL scheme set through a scheme handler (which is how Capacitor serves `capacitor://localhost`) comes from commenters, including Capacitor and Cordova users; the page has no WebKit engineer statement that the limit is intended or permanent. [WebKit bug 206741](https://bugs.webkit.org/show_bug.cgi?id=206741)
- [Apple rule] Guideline 2.5.9: apps that alter or disable "native user interface elements or behaviors will be rejected. For example, apps should not block links out to other apps or other features that users would expect to work a certain way." [2.5.9](https://developer.apple.com/app-store/review/guidelines/#2.5.9)
- [Repo] `capacitor.config.ts`: `webDir: 'dist'`, `contentInset: 'never'`, `preferredContentMode: 'mobile'`, `allowsLinkPreview: false`, CapacitorHttp and CapacitorCookies enabled, SplashScreen `launchAutoHide: false`, Keyboard `resize: 'none'`. `LogbookViewController.swift` re-enables scroll bounce, sets `alwaysBounceVertical`, `contentInsetAdjustmentBehavior = .never`, link previews off.
- [Repo] `@capacitor/ios` 8.5.3 `WebViewDelegationHandler.swift` implements `webViewWebContentProcessDidTerminate` by resetting the bridge and calling `webView.reload()`.
- [Repo] Web storage use: offline outbox and cache through `idb-keyval` (`src/api/outbox.ts`, `src/main.tsx`); localStorage keys for onboarding and feature flags, the goal reminder switch (`logbook.goalReminders`) and the pre-signup privacy choice (`logbook.consent.pending`). The consent setting itself lives on the server (`user_settings.consent`). `src/lib/sw.ts` skips service worker registration when native. Auth cookie is set with `expires`, `httpOnly`, `sameSite: 'Lax'` (`apps/api/src/auth.ts`).

### Inferences
- Because the web build is embedded and nothing is fetched as code, 2.5.2 is satisfied and 4.7 is not triggered. An over-the-air JS update service would change that analysis.
- Eviction deletes the whole origin at once. For Logbook that means: the user looks signed in (cookie lives in the native jar, not subject to the policy) but local flags reset. Each flag needs a sane missing-value behaviour: onboarding flags should fall back to server state so a returning user is not shown first-run again; the reminders switch falling back to "off" would silently stop reminders while pending notifications already scheduled keep firing until they run out; unsent outbox writes would be lost.
- The seven-day ITP purge is documented for Safari; whether it applies to a first-party `capacitor://localhost` origin in an app is not stated by WebKit. Treat web storage as cache either way.
- The auth cookie has an expiry, so it is not a session-only cookie and should survive process death; this needs a device test rather than an assumption because the cookie crosses the CapacitorHttp and WKWebView stores.
- WKWebView's content process can be killed under memory pressure independently of the app; Capacitor reloads the page. The app must restore route and unsaved input after such a reload (journal entry in progress, assistant draft).
- `user-select: none` on chrome and lists is normal app behaviour; keep it off user-authored text so copy works.

### Gaps
- Whether CapacitorHttp delivers response bodies incrementally (needed for live assistant text) is not documented. I did not trace how Logbook streams assistant text; test on device.
- Whether WKWebView in a non-browser app can obtain persistent storage mode: WebKit only describes the Home Screen web app heuristic.
- No primary source states whether `-webkit-touch-callout`, pull to refresh or scroll bounce choices affect review; these are feel items.
- Keyboard handling (`resize: 'none'` plus custom `--kb` variable) has no rule attached; correctness is a device test on every input, including with a hardware keyboard on iPad.

## 6. Performance, crash reporting and offline behaviour

### Takeaway
Apple gives a goal (first frame within 400 ms) and an enforcement (the watchdog terminates slow or unresponsive launches) but no published pass/fail number for review. Logbook has no crash or error reporting today; the zero-label option is Apple's own Organizer plus MetricKit, and any third-party or first-party error upload adds Diagnostics to the nutrition label.

### Cited Findings
- [Apple guidance] "we need to hit the goal of rendering our first frame within 400 milliseconds. That's so that we have pixels displayed to the user during the launch animation". Cold launch "after reboot, or when your app has not been launched for very long time"; warm launch when the app is still in memory caches; resume when the process is alive. [WWDC19 session 423, Optimizing App Launch](https://developer.apple.com/videos/play/wwdc2019/423/)
- [Apple guidance] "An app that takes too long to launch may frustrate the user, and on iOS, the watchdog will terminate it if it takes too long." [Reducing your app's launch time](https://developer.apple.com/documentation/xcode/reducing-your-app-s-launch-time)
- [Apple guidance] "The operating system employs a watchdog that monitors launch times and app responsiveness, and terminates unresponsive apps. Watchdog terminations use the code 0x8badf00d". "The watchdog terminates apps that block the main thread for a significant time." The sample report shows "exhausted real (wall clock) time allowance of 19.97 seconds" for a scene-create event. [Addressing watchdog terminations](https://developer.apple.com/documentation/xcode/addressing-watchdog-terminations)
- [Apple rule] Guideline 2.4.2: "Apps should not rapidly drain battery, generate excessive heat, or put unnecessary strain on device resources." [2.4.2](https://developer.apple.com/app-store/review/guidelines/#2.4.2)
- [Apple rule] Guideline 2.1(a): "Make sure your app has been tested on-device for bugs and stability before you submit it, and include demo account info (and turn on your back-end service!) ... - [Apple guidance] "On average, over 40% of unresolved issues are related to guideline 2.1: App Completeness, which covers crashes, placeholder content, incomplete information, and more." "Make sure to thoroughly test on devices running the latest software". [App Review](https://developer.apple.com/distribute/app-review/)
- [Apple guidance] "TestFlight and the App Store collect crash reports for every submitted version of your app." "The Crashes organizer presents crash reports from customers who share diagnostic and usage information ... TestFlight users of your app automatically share crash reports with you". High memory terminations appear as `JetsamEvent_` logs. [Acquiring crash reports and diagnostic logs](https://developer.apple.com/documentation/xcode/acquiring-crash-reports-and-diagnostic-logs)

[MetricKit](https://developer.apple.com/documentation/metrickit)
- [Apple rule] Nutrition label: "'Collect' refers to transmitting data off the device in a way that allows you and/or your third-party partners to access it for a period longer than what is necessary to service the transmitted request in real time." Crash Data: "Such as crash logs". Performance Data: "Such as launch time, hang rate, or energy use". ### Inferences
- Three workable crash and error options, with their consequences:
  1. Apple only: Xcode Organizer crash and hang reports plus optional MetricKit payloads kept on device. No SDK, no manifest change, no label change (data is collected by Apple, from users who opted in to share). Blind spot: JavaScript errors inside the web view never appear, because a thrown JS error is not a native crash.
  2. First-party error log: ErrorBoundary and `window.onerror` post a small report to the Logbook API. No third party, but if reports are retained they are "collected": add Diagnostics (Crash Data and/or Other Diagnostic Data) to the label and to `NSPrivacyCollectedDataTypes`, linked to the user if the request is authenticated. Strip journal text, health values and prompts from reports.
  3. Sentry (`@sentry/capacitor`): covers native and JS with symbolication. Adds a third-party SDK, three required reason categories via its own manifest, Diagnostics on the label, and needs configuration to stop IP and user identity collection and to scrub request bodies. Verify Capacitor 8 and SPM support before choosing.
- Option 1 plus a minimal option 2 is the smallest privacy footprint that still sees JS failures.
- Apple's 400 ms figure is a design goal for the first frame, which for Logbook is the native launch storyboard; perceived launch is storyboard to first web paint, so the measurable target is time until `hideSplash` on the oldest supported phone.
- The 20-second scene-create allowance in Apple's sample report is an example, not a published limit; do not rely on it.

## 7. Deep links, iPad and Mac compatibility, Dynamic Type, haptics, local notifications

### Takeaway
None of these block a 1.0 on their own, but each has a concrete test: the app must run on iPad even if iPhone only, the custom scheme must carry no secrets, text must scale without breaking layouts, and pending notifications must stay far below 64.

### Cited Findings
- [Apple rule] Guideline 2.4.1: "To ensure people get the most out of your app, iPhone apps should run on iPad whenever possible." [2.4.1](https://developer.apple.com/app-store/review/guidelines/#2.4.1)
- [Practitioner] (opened 2026-11-10 through the fetch tool; no Apple staff reply in any of the three) Developers report iPhone-only apps being tested and rejected on iPad: thread 816230 (February 2026, SIM and SMS binding fails on iPad, device family set to iPhone); thread 802147 (September 2025, "App Review keeps rejecting the app, citing iPad compatibility issues" with device family iPhone only; the developer resubmitted with iPad support). Thread 26501 (2015 to 2016) has the older replies: an iPhone-only app "can and will still be run on an iPad" at iPhone size, and the advice "to have always your app ready for testing on iPad even" when it is iPhone only. [Forums 816230](https://developer.apple.com/forums/thread/816230) ; [Forums 26501](https://developer.apple.com/forums/thread/26501) ; [Forums 802147](https://developer.apple.com/forums/thread/802147)
- [Apple rule] "Users running macOS 11 or later on Macs with Apple silicon can access iPhone and iPad apps through the Mac App Store, provided no edits are made to the app availability." Opt out: "Under Apple Silicon Mac Availability, deselect 'Make this app available'". [App Store Connect Help](https://developer.apple.com/help/app-store-connect/manage-your-apps-availability/manage-availability-of-iphone-and-ipad-apps-on-macs-with-apple-silicon/)
- [Apple rule] Universal links: "To associate a website with your app, you need to have the associated domain file on your website and the appropriate entitlement in your app." The file is `apple-app-site-association` (no extension) at `https://<fully qualified domain>/.well-known/apple-app-site-association`; each subdomain "requires its own entry" and "must serve its own apple-app-site-association file". "Starting with macOS 11 and iOS 14, apps no longer send requests for apple-app-site-association files directly to your web server. Instead, they send these requests to an Apple-managed content delivery network". "Apple's content delivery network requests the apple-app-site-association file for your domain within 24 hours. Devices check for updates approximately once per week after app installation." [Supporting associated domains](https://developer.apple.com/documentation/xcode/supporting-associated-domains)
- [Vendor docs] Capacitor: add the Associated Domains capability with `applinks:yourdomain.com`; handle `appUrlOpen` "on app startup"; test on a physical device. [Capacitor deep links](https://capacitorjs.com/docs/guides/deep-links)
- [Vendor docs] "Generally, an app should never send sensitive data through a Custom URL scheme deep link"; "newer techniques such as Universal Links are more secure as they rely on actual web domain ownership"; "PKCE must be used for oAuth2 in Capacitor apps". [Capacitor security](https://capacitorjs.com/docs/guides/security)
- [Vendor docs] Dynamic Type keywords: `font: -apple-system-body`, `-apple-system-headline` and others "represent an entire style, including size and weight"; "iOS has dynamic type behavior, which can provide an additional level of fit and finish to your content." [WebKit: Using the System Font in Web Content](https://webkit.org/blog/3709/using-the-system-font-in-web-content/)
- [Practitioner] The keyword tracks the system Text Size setting in WKWebView; it also forces the system font, so reading its computed size and applying it to your own font is the usual workaround; on macOS Safari it resolves to 13px. [furbo.org: Dynamic Type on the Web](https://furbo.org/?p=2791) ; [Use Your Loaf: Using Dynamic Type with Web Views](https://useyourloaf.com/blog/using-dynamic-type-with-web-views/) ; [WebKit bug 230348](https://bugs.webkit.org/show_bug.cgi?id=230348) (search summaries only; unverified, not opened in the 2026-11-10 pass)
- [Apple guidance] Larger Text label: "You can indicate that your app supports Larger Text if users can enlarge text to at least 200% or the maximum font size for the system." "Body text in the primary iPhone, iPad, and Mac views should increase in size without affecting readability through overlapping layouts or severe truncation." "If your app uses a web view as part of its common tasks, provide a font size controller or let Safari handle this task". "some features, like Tab Bars, don't grow with dynamic text ... Consider other ways to make those elements accessible, such as the Large Content Viewer." "Don't rely on system-provided assistive technology like Zoom". [Larger Text evaluation criteria](https://developer.apple.com/help/app-store-connect/manage-app-accessibility/larger-text-evaluation-criteria)
- [Apple guidance] Haptics: "Use system-provided haptic patterns according to their documented meanings." "Use haptics consistently". "Avoid overusing haptics." "Make haptics optional. Let people turn off or mute haptics, and make sure people can still enjoy your app or game without them." Notification haptics are for task outcomes, impact for physical metaphors, selection while values change. [HIG Playing haptics](https://developer.apple.com/design/human-interface-guidelines/playing-haptics)
- [Apple guidance] Local notification cap: "An app can have only a limited number of scheduled notifications; the system keeps the soonest-firing 64 notifications (with automatically rescheduled notifications counting as a single notification) and discards the rest." This sentence is on the deprecated `UILocalNotification` class page; the `UNUserNotificationCenter` pages read do not repeat it. [UILocalNotification](https://developer.apple.com/documentation/uikit/uilocalnotification)
- [Apple guidance] "Once scheduled, a notification request remains active until its trigger condition is met, or you explicitly cancel it." Repeating calendar triggers are rescheduled by the system. [Scheduling a notification locally from your app](https://developer.apple.com/documentation/usernotifications/scheduling-a-notification-locally-from-your-app)
- [Vendor docs] `@capacitor/local-notifications`: since 8.3.0 `schedule()` requests notification permission if not yet granted; `interruptionLevel: timeSensitive` "Requires the Time Sensitive Notifications capability"; `critical` needs the Critical Alerts entitlement; iOS foreground presentation is controlled by `presentationOptions`; the page does not mention a 64 limit. [Capacitor Local Notifications](https://capacitorjs.com/docs/apis/local-notifications)
- [Apple rule] Guideline 4.5.4: "Push Notifications must not be required for the app to function" and must not be used for marketing without opt in. Written for push. [4.5.4](https://developer.apple.com/app-store/review/guidelines/#4.5.4)
- [Repo] Deep links: scheme `logbook` in Info.plist; `src/lib/native.ts` turns `logbook://settings?strava=connected` into in-app navigation; `apps/api/src/routes/strava.ts` builds that landing URL after the server-side OAuth exchange. No associated-domains entitlement. Dynamic Type: `src/app/dynamicType.ts` probes `-apple-system-body` (17px at default) and scales the root font size by the ratio. Reminders: `src/features/goals/reminders.ts` schedules at most 7 notifications with ids 7000 to 7006 and cancels the same ids when turned off.

### Inferences
- With device family `1` the app runs on iPad in a scaled iPhone presentation; with `1,2` it is a real iPad app and needs layouts and screenshots. In both cases a reviewer may use an iPad.
- On iPad and Mac the Health path differs: HealthKit reads work on iPadOS 17 and later but an iPad usually holds little data; on Mac `isHealthDataAvailable()` is false. Opting out of Mac and Vision Pro availability removes two untested surfaces.
- The custom scheme is acceptable for the Strava return because it carries only a status flag; another app could register the same scheme and receive that flag, which is harmless, but any future token in a deep link would not be.
- Logbook's root-font scaling means the whole rem-based UI grows with the system setting; at the largest accessibility sizes the factor is large (over 300% at AX5 per Apple's Larger Text criteria page, verified 2026-11-10; see Gaps), so fixed-height rows, the tab capsule, charts and sheets are the likely breakpoints. Capping the factor is a design choice; claiming the Larger Text label requires reaching 200% or the system maximum.
- The 64 cap comes from a deprecated API page; it is widely treated as still true for `UNUserNotificationCenter`. Logbook's 7 pending requests are safe either way.

### Gaps
- No Apple page read states which device App Review uses or that iPhone-only apps are reviewed on iPad; evidence is practitioner reports.
- No Apple statement found on whether `UIFeedbackGenerator` output obeys the system haptics switch; assumed but not cited.
- The exact scale of `-apple-system-body` at each accessibility size was not found in a primary source. Partly closed (verified 2026-11-10): Apple's Larger Text criteria page states "Dynamic Type on iOS, for example, reaches sizes larger than 200% at the AX3 size, and allows body text sizes over 300% at the AX5 size." So the "about three times" figure in Inferences has an Apple source for the top size; per-step values are still not sourced.
- Apple Vision Pro availability rules live on a separate App Store Connect Help page that was not read.

## 8. Guideline 4.2 and web-wrapped apps

### Takeaway
4.2 is judged on what the reviewer experiences, not on the plugin list. Logbook's protection is that its core flows are its own (not a third-party site), it is bundled and works offline at shell level, and it uses native capabilities that a website cannot (HealthKit, scheduled local notifications, haptics, share sheet). The residual risk is any moment that looks like a browser.

### Cited Findings
- [Apple rule] "Your app should include features, content, and UI that elevate it beyond a repackaged website. If your app is not particularly useful, unique, or 'app-like,' it doesn't belong on the App Store." [4.2](https://developer.apple.com/app-store/review/guidelines/#4.2)
- [Apple rule] 4.2.2: "Other than catalogs, apps shouldn't primarily be marketing materials, advertisements, web clippings, content aggregators, or a collection of links." 4.2.3: "(i) Your app should work on its own without requiring installation of another app to function. (ii) If your app needs to download additional resources in order to function on initial launch, disclose the size of the download and prompt users before doing so." 4.2.6: apps "created from a commercialized template or app generation service will be rejected unless they are submitted directly by the provider of the app's content". [4.2](https://developer.apple.com/app-store/review/guidelines/#4.2)
- [Apple guidance] "Web clippings, content aggregators, or a collection of links: Your app should be engaging and useful, and make the most of the features unique to iOS. Websites served in an iOS app, web content that is not formatted for iOS, and limited web interactions do not make a quality app." "Substandard user interface: Apple places a high value on clean, refined, and user-friendly interfaces." [App Review](https://developer.apple.com/distribute/app-review/)
- [Apple rule] 2.5.1: "Apps should use APIs and frameworks for their intended purposes and indicate that integration in their app description. For example ... HealthKit should be used for health and fitness purposes and integrate with the Health app." [2.5.1](https://developer.apple.com/app-store/review/guidelines/#2.5.1)
- [Practitioner] A Capacitor app whose core booking flow ran inside a third-party web page was rejected twice under 4.2; the developer paraphrases the feedback as "the experience is not sufficiently differentiated from web browsing and that features such as Core Location or sharing alone are not robust enough". A reply: 4.2 concerns what the reviewer experiences, not the plugin list; describe features in plain terms in App Review notes. No Apple staff reply. Thread created January 2026. [Apple Developer Forums 812889](https://developer.apple.com/forums/thread/812889)
- [Practitioner] Commonly cited mitigations: offline handling instead of a browser error page, native navigation feel, device integration reachable from the first screens, and review notes that list native features. (corrected 2026-11-10: both threads were opened through the fetch tool and support less than this. Forums 806726: ten 4.2 rejections of a WebView-based app; replies say to build the remaining pages natively; Apple's reply only recommends an App Review consultation. Forums 126359, November 2019: a website wrapper rejected twice under 4.2; the one reply says the app must do things "beyond a progressive web application can do" and to add native features "where it makes sense". Neither discusses offline handling or review notes; those two items are unverified.) [Forums 806726](https://developer.apple.com/forums/thread/806726) ; [Forums 126359](https://developer.apple.com/forums/thread/126359)

### Inferences
- Logbook differs from the rejected pattern in the ways that matter: the UI is authored for iOS and bundled, the data is the user's own, and there is no public website offering the same thing. That should be said plainly in review notes.
- Checklist of "browser tells" to remove before review: any default WebKit error or blank page (network loss, 500, expired session); selection handles or the copy callout appearing on buttons and chrome; pinch or double-tap zoom; a visible grey flash on tap; scroll that stops dead or chrome that scrolls with content; a link that navigates the whole web view to an external site; the keyboard covering inputs; slow first paint after the launch screen; system alerts from `window.alert`/`confirm` showing a "localhost" style title.
- Native capabilities should be visible early: Health connect in onboarding, the notification nudge, haptic feedback on primary actions, the share sheet. Guideline 2.5.1 asks that the HealthKit integration be named in the description.
- Suggested review note content (plain language): what the app does; that all content is bundled and works without loading a website; the native features used (Apple Health read, reminders, haptics, share); the demo account; where to find Health and reminders.

### Gaps
- Apple publishes no objective test for 4.2. No Apple staff statement was found on Capacitor or hybrid apps specifically (still true after the 2026-11-10 pass: the one Apple reply seen, in Forums 806726, only points to a consultation).
- No data on rejection rates for Capacitor apps.
